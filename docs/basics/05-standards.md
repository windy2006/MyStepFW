# 开发规范与目录归属

修订日期：2026-10-24。适用于当前框架。

## 本篇目标与调用场景

从框架入口与目录职责建立正确的开发上下文，明确功能由哪个阶段、文件和对象承担。

## 5. 开发规范：先确定归属，再写功能

普通应用放在自己的 `app/应用名/`，核心类必须按规范声明为同名 `myStep` 子类并保存在应用目录。页面按 `module/` 与 `template/` 对应拆分。不要把应用服务类放进根 `lib/` 来解决自动加载问题；需要时从本应用显式加载。

插件使用 `plugin/标识/class.php` 和 `plugin_标识 implements interface_plugin`；生命周期方法、前置脚本和宿主初始化各有明确触发条件。应用规范保留在 [app/README.md](../development/app/README.md)，插件规范保留在 [plugin/README.md](../development/plugins/README.md)。

配置、路由及类加载声明属于受信开发内容，不接收用户提交的 PHP 文件名或回调。请求输入先验证；数据库值使用参数绑定；展示按 HTML、URL、JSON 等上下文编码。状态修改走 POST／合适的非安全请求方法和 CSRF 校验，不依靠隐藏按钮控制权限。

当前不统一新增 PHP 8 原生类型约束；通过中文功能说明、PHPDoc 参数、返回、异常及示例完善可读性，并保持 PHP 7.4 和既有子类兼容。新增公共方法同步检查框架、应用、插件、示例与测试中的调用点，详见[功能设置](03-management.md)。


## 版本号维护

系统、应用和插件统一采用[语义化版本控制 SemVer 2.0.0](https://semver.org/lang/zh-CN/)，正式版本写成 `MAJOR.MINOR.PATCH`，各段为无前导零的非负整数。

| 变化性质 | 递增规则 | 示例 |
| --- | --- | --- |
| 兼容的问题修复或性能修正 | 递增修订号 | `1.2.3` → `1.2.4` |
| 向后兼容的新功能或公开接口弃用声明 | 递增次版本号，修订号归零 | `1.2.3` → `1.3.0` |
| 不兼容的公开接口或使用约定变更 | 递增主版本号，其余归零 | `1.2.3` → `2.0.0` |

本轮框架整体改造统一归入 `2.x` 版本线，分批完成的子项不单独开启新主版本；旧入口统一替换归档为 `2.3.0`。这是本轮整体改造的版本归档约定，兼容性变化仍须明确列出。待发布版本的标注修正不额外递增，其他版本维护继续按本节规则执行。

公开约定包括方法签名、路由及参数、模板语法、钩子协议和配置／数据格式。按实际兼容性判断版本等级，不能将新增功能一律作为修订号，也不能仅因改动文件多就递增主版本。系统与各组件分别判断其兼容性，版本号无需一致。

每次代码变更同步维护系统 `config/version.php`；涉及应用时维护对应 `app/应用名/info.php` 的 `ver`，涉及插件时维护对应 `plugin/插件名/info.php` 的 `ver`。模块、模板、JavaScript 和样式等功能代码也属于所属组件的版本范围；未修改的应用和插件不批量加号。历史 `1.0` 等两段版本在对应组件下一次变更时按 `1.0.0` 基线选择新版本，例如兼容修复为 `1.0.1`，新增功能为 `1.1.0`。

一次完整变更统一递增一次；该批变更的修正、验证及随后的 GitHub 提交不重复加号。独立的新变更再次递增；不得覆盖已发布版本的内容或将版本号回退。仅整理文档或注释、未改变功能代码时，不单独制造功能版本。

GitHub 提交标题统一为 `v系统版本 - 中文更新摘要`，例如 `v2.1.0 - 完善 API 管理与框架指南`。相关应用和插件版本写入提交说明；同版本的文档同步提交也使用该版本前缀。历史提交补充标题时按其原有版本声明填写，不为修改标题改变当时的代码树。

GitHub 提交前必须核对：

1. 确认提交标题与系统版本一致，根据待提交变更确认系统及相关应用、插件的版本均已正确递增，且版本声明、兼容性说明、示例和验证结果一致。
2. 已安装插件登记版本与实际部署版本同步，保留启停、绑定和排序；运行数据不作为源码提交。
3. 更新源的 `plugin/manager/version.php` 是发布清单，每次提交前必须累计记录当前系统版本的新增、修改、删除文件；移动同时列旧、新路径。同版本的文档和历史同步提交也要补入。`check_app.php`、`check_plugin.php` 是远程检查缓存，均不能代替系统或组件自身的版本声明。
4. GitHub 更新历史在提交后根据真实提交生成中文记录，明确变更版本；`docs/backup/`继续排除，不把未提交内容写成已经发布。

### 提交前生成升级文件清单

清单按**系统版本**组织，`file` 使用以 `/` 开头的网站根目录相对路径，不能写服务器绝对路径。版本声明 `config/version.php` 和清单自身也纳入更新。详见 [manager 的版本记录与升级包](../showcase/plugins/manager.md#版本记录与升级包)。

本机开发工具 `maintenance/sync-manager-release.php` 从 Git **暂存区**读取待发布版本和文件。它自动找到当前版本首次出现之前的最后提交作为基线，统计本版本的完整差异。同一版本多次提交不会丢掉前面的改动；文件移动按删除旧路径、新增新路径处理。站点私有配置、数据库、缓存、生成资料和本机测试维护文件按发布规则过滤。

```sh
# 在发布用Git仓库中，先暂存本批准备提交的具体文件。
git add -- lib/示例类.class.php config/version.php

# 使用PHP 7.4执行本机维护工具；参数中的路径换成实际位置。
php /本机网站/maintenance/sync-manager-release.php \
  --repository=/发布仓库 --write --info='本版中文更新说明'

# 检查生成的文件清单和人工维护的setting/code后，暂存清单。
git add -- plugin/manager/version.php
php /本机网站/maintenance/check-release.php --repository=/发布仓库
```

`--write` 只更新工作区清单，不自动暂存、提交或推送；存在未暂存的清单修改时拒绝覆盖。单独使用 `--check` 可只读核对清单；`--report=/本机报告.json` 可保存完整的增改删明细及被保护路径的过滤原因。发布检查发现漏记、过时路径、历史记录被覆盖或未来版本时返回失败。

首次配置本机发布仓库时，执行以下命令安装检查钩子。`pre-commit`核对暂存区，`pre-push`通过独立临时索引核对实际待推送提交，不影响开发中的暂存状态。已有其他用途的钩子时，安装器保留原文件并要求人工整合；不能直接覆盖。工具和钩子不随源码发布，新发布仓库须重新安装。

```sh
php /本机网站/maintenance/install-release-hooks.php --repository=/发布仓库
```

配置结构变化通过人工审阅的 `setting` 合并，必要的数据迁移通过 `code` 处理。生成工具只负责文件差异，不推断数据库或配置迁移，不用覆盖用户配置的方式代替迁移。GitHub Release 和中文更新历史是展示资料，不能代替 manager 的文件清单。仅完善发布记录和文档不单独递增功能版本。

## 操作步骤与注意事项

相关配置以当前框架设置和对应应用覆盖为准。普通应用使用同名myStep子类；类与模块放在自己的目录。文件系统路径和浏览器URL分别生成，不复用本机绝对目录作为可发布设置。

## 验证与进一步阅读

示例中的文件、数据库和变量按本篇前提准备；涉及写入时使用独占临时目录或隔离库，按明确返回值和异常验证。源码中的public/protected/private、引用参数和可选接口是实际契约，不能只按方法名猜测返回或能力。
