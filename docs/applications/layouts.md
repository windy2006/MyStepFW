# myStep、CMS、Admin 顶层结构实例

整理日期：2026-10-18。目标运行环境：PHP 7.4。此处是具体应用的源码参照；通用规则统一在 app/README.md。

本篇逐项核对 `app/myStep/`、`app/CMS/` 根目录的文件及直接子目录，只说明子目录整体职责，不展开内部文件清单。它补充 [应用编写规范](../../app/README.md)，以现有加载代码为依据说明哪些文件由框架识别，哪些由应用或管理功能显式调用。

普通应用遵循：所有专属源码和资源归本应用目录；核心文件名、核心类名和应用目录名一致，核心类继承 myStep。myStep 是框架核心特例，其核心类位于公用 `lib/myStep.class.php`，不在 `app/myStep/` 重复定义。

## 2. 顶层目录配置规则

| 目录 | myStep | CMS | 作用及配置关系 |
| --- | --- | --- | --- |
| `asset/` | 有 | 有 | 应用 CSS、JS、图片等资源。框架收集基础样式／脚本及当前模板风格下的对应文件，其他资源通过应用资源入口访问。应用专属资源归本目录，公用资源才归网站 `static/`。 |
| `config/` | 有 | 有 | 设置编辑界面的字段名称、说明、控件类型和结构。与根目录 `config.php` 的配置键对应；它自身不是当前配置值文件。 |
| `language/` | 有 | 有 | 界面语言字符串。按 `gen.language` 加载应用同语言文件，与 myStep 公共语言叠加。与 `config/` 中“设置字段说明的语言版本”分别维护。 |
| `module/` | 有 | 有 | 每项功能的处理代码。按功能拆分，与相应模板建立清楚对应关系；模块路径由框架分发规则和应用分发代码共同决定。当前名称为 module，不是 model。 |
| `template/` | 有 | 有 | 主布局和功能模板。由 `template.path`、`template.style`、`template.name` 决定位置和默认模板；同一功能可以有列表、输入等多个对应模板。 |
| `sample/` | 有 | 无 | myStep 的功能演示资料，由示例功能显式使用；不是所有应用都必须提供的框架目录。 |
| `install/` | 无 | 有 | CMS 安装检查所进入的安装过程及所需资源。由应用安装检查显式引入，普通应用有独立安装需求时采用；不因为目录存在就自动运行。 |
| `website/` | 无 | 有 | CMS 多站点配置，由 CMS 核心及站点管理功能按站点标识选择；这是 CMS 自己的扩展，不是框架为所有应用自动扫描的目录。 |

目录归纳分为两层：五个共用组织目录是 `asset`、`config`、`language`、`module`、`template`；`sample`、`install`、`website` 是按应用功能增加的目录。新应用按需求采用，不机械复制全部目录。

## 3. 根目录脚本逐项说明

### 3.1 info.php：应用身份与元信息

返回 PHP 数组，两个应用均包含 `name`、`app`、`ver`、`intro`、`copyright`。`app` 与目录名一致，显示名称 `name` 可以使用中文，不代替程序标识。

框架通过应用目录中的 `info.php` 识别应用、读取元信息并发现可登记的路由来源，管理功能也据此展示应用清单。保持该文件为元信息声明，避免执行业务处理。

### 3.2 应用名.class.php：应用核心类

CMS 对应 `app/CMS/CMS.class.php`、类名 `CMS`，声明 `class CMS extends myStep`。框架按 `PATH + 应用名 + .class.php` 加载并实例化，将当前控制器置于 `$mystep`。

核心类继承框架资源和能力，集中实现应用公共方法及必要生命周期扩展。CMS 当前实现登录、退出、日志、带日志的跳转、`preload()`、`shutdown()` 和 `checkPower()`，没有把所有页面功能集中在类中。

myStep 核心类位于 `lib/myStep.class.php`，因此应用根目录没有 `myStep.class.php`。这个核心特例不能用于省略普通应用的同名核心类。现有框架虽兼容缺少主类时回退 myStep，新应用仍按已确认规范提供自己的核心类。

### 3.3 config.php：当前应用配置值

返回本应用配置数组，运行时合并到全局配置对象。只需要声明本应用使用或覆盖的项目，无须复制所有全局配置。

- myStep 包括页面缓存、后台入口 `gen.path_admin`、标题、模板和数据库自动连接设置。
- CMS 包括域名策略、后台入口 `web.path_admin`、数据库、内容、模板、会话、列表条数、缓存时效及水印等应用设置。
- 两者的后台入口配置键不同，应沿用相应调用代码，不因都叫“后台路径”就混用。
- 新增配置键时，同步根配置、设置编辑结构和说明、读取代码及保存后的关联处理。

本地路径保存为网站根相对路径，例如 `app/CMS/template`，运行时由 ROOT 解析。模板 style 是风格标识，后台 path_admin 是 URL 入口，它们都不是服务器绝对磁盘目录。细节见 [路径规范](../framework/paths.md)。

### 3.4 config_default.php：应用安装初始配置

CMS 提供此文件，结构与当前配置对应，作为安装表单和生成实际配置的基础。安装流程明确加载它，再将确认后的设置保存为当前应用配置。

它不是请求运行时自动覆盖／补齐 `config.php` 的文件，也不等于 `config/` 目录里的默认设置说明。myStep 根目录没有此文件；框架首次安装使用的是网站根 `config/config_default.php`。

### 3.5 config_入口名.php：匹配路由入口的配置覆盖

CMS 的 `config_admin_cms.php` 对应后台路由入口 `admin_cms`，当前设置为关闭页面缓存并将模板风格设为 `admin`。

命中路由时，框架读取应用基础配置，然后尝试 `config_匹配请求首段.php`；后台入口匹配这个约定，所以命名应关联路由首段。该机制不代表框架会无条件扫描所有 `config_*.php`。

例如本应用后台入口由 `admin_cms` 改成 `manage`，对应入口配置需要调整为 `config_manage.php`，路由及相关 URL 也应同步。模板风格仍由文件中的 `template.style` 控制，不需要跟随入口名称改为 manage。

普通应用无分入口覆盖需求时不必提供此文件。域名绑定和 URL 前缀可能影响实际匹配上下文，应按实际路由核对。默认应用入口分支不会仅因出现同名文件就自动完成此层覆盖。

### 3.6 lib.php：本应用可复用函数及辅助加载

两个应用分别采用 `namespace app\myStep;` 和 `namespace app\CMS;`。它是应用级函数库，与网站根公用 `lib/` 目录职责不同。

- myStep 提供后台登录检查、数据浏览接口、日志数量读取和自动完成等函数。
- CMS 提供安装／登录检查、用户与附件接口、业务数据缓存、栏目／标签处理、链接／分页生成及模板标签解析等函数。

框架准备应用时加载此文件；API、应用专项功能和插件模块等分支也可能显式引入它。因此保持其顶层以声明和明确辅助加载为主，避免直接输出页面或执行业务写入。

应用辅助类放在应用内，并在合适位置明确 require；不要为便于类加载把应用专属实现放进公用 lib。命名空间内引用框架类使用完整类名或明确 use。

### 3.7 global.php：页面共享准备

负责当前应用页面共享的变量、导航上下文或模板赋值。

- myStep 计算后台根链接、当前路径，并向可用的主模板赋入后台／退出链接、数据库配置状态等数据，同时调整页面缓存模式。
- CMS 检查安装状态、取得栏目缓存、准备栏目树形数据，并建立应用 URL 根 `ROOT_APP`。

默认应用入口在执行 `index.php` 前加载；框架 `getModule()` 页面分支也会加载。插件文件模块的布局装配分支还有自己的包含位置。不能把 global 理解为所有请求分支、所有时刻必执行的“全局配置脚本”，也不能假定它执行时总已有 `$tpl`。

### 3.8 index.php：默认页面分发与组装

由框架默认应用入口分支调用，不是另一个网站启动器。

- myStep 默认入口将访问跳转到配置的框架后台路径。
- CMS 默认入口注册应用展示标签、选择前台功能模块、准备页面缓存和主模板、包含对应模块、合并栏目导航，并将子模板内容组装进主模板。

自定义路由命中后可走另一条处理链，不一定经过应用 index。index 保持入口与公共装配职责，各功能保留在自己的模块及对应模板中。

### 3.9 route.php：路由、API 及可选格式声明

应用通过 `$rule` 声明路径和处理器，通过 `$api` 声明 API 名到方法的对应；格式扩展可按框架接口声明 `$format`，当前这两个应用主要定义 rule 和 api。

- myStep 声明后台检查及模块分发、通用 API／模块入口、语言和设置接口、验证码、错误响应以及 sitemap／RSS／Atom 等框架入口。
- CMS 声明后台入口的安装检查、登录检查、模块分发链，以及 user、get、attachment 等 API。

框架读取应用配置后汇总各 route，写入网站共享路由注册表。该文件可能只在路由重建时被执行，避免在里面放每次请求必须执行的初始化或业务写入。

路由使用的应用函数由 lib 提供，核心类静态方法由同名核心类提供。路由源码留在应用目录，生成的根 `config/route.php` 不作为应用开发入口。

### 3.10 plugin.php：应用使用的插件标识清单

返回插件标识数组。myStep 当前绑定 manager，CMS 当前数组含一个空项；空项没有对应启用插件，不会因此加载插件，新配置无插件时宜写空数组。

框架 start 读取该清单，与全局已启用插件列表核对后登记插件。该文件声明“本应用使用哪些插件”，不是插件实现、全局启用状态或插件页面布局脚本。

### 3.11 plugin_addon.php：插件模块页面的应用布局适配

CMS 提供该脚本。框架 `myStep::module()` 执行登记的文件型模块后，在存在有效 `$tpl` 的分支中，加载当前应用的公共准备及 plugin_addon，随后把模块内容放入主模板输出。

CMS 在这里注册 info 标签、为栏目生成链接，并向布局填充导航循环和栏目数据，让插件模块页面能使用 CMS 的外层展示环境。

它是“插件模块页面嵌入当前应用”时的补充，不是所有页面自动运行的脚本，不是插件安装钩子，也不能替代 plugin.php。只有应用需要这类适配时才提供。

### 3.12 setting_expand.php：配置保存时的关联处理

两个应用都有，用于设置值发生变化时同步关联资源。

- myStep 在后台入口改变时更新菜单链接、当前入口值及路由登记，并安排页面跳转。
- CMS 在后台入口改变时重命名对应的 `config_入口名.php` 并重新登记路由；安装流程也会显式调用它处理初始设置。

旧后台设置保存逻辑在更新配置对象和保存文件前显式 include 此文件。它依赖保存调用方提供的 `$app`、`$config`、`$router`、`$ms_setting` 及提交设置等上下文，没有统一的独立函数签名。

因此，只有放置文件并不会自动获得保存钩子；新设置管理实现需要明确接入同等关联处理。当前 Admin 在自己的 setting_expand.php 中显式实现 myStep 菜单和 CMS 入口配置的等效关联，不直接 include 依赖旧后台局部变量和 PATH 的目标脚本；其他应用扩展仍需明确接入。

### 3.13 sitemap.php：应用站点地图输出

CMS 提供站点地图专项脚本。框架 sitemap 路由通过 `myStep::appFunc('sitemap')` 选择核心应用，再加载其根目录同名脚本。

CMS 脚本选择站点和配置、准备数据连接及缓存，填充 sitemap 模板中的地址、日期、优先级等数据，输出 XML。对应其应用模板，不通过普通 index 页面分发。

### 3.14 rss.php：应用 RSS 订阅输出

由 RSS 框架专项入口通过 appFunc 选取当前核心应用的 rss 脚本。CMS 组织站点信息和近期文章摘要，渲染 rss 模板并输出 XML。

### 3.15 atom.php：应用 Atom 订阅输出

由 Atom 框架专项入口通过 appFunc 选取当前核心应用的 atom 脚本。CMS 组织站点、更新时间、文章、标签等订阅信息，渲染 atom 模板并输出 XML。

三个专项脚本共同遵循“框架入口名 → 当前核心应用根同名 PHP → 对应输出模板”的关联。getCore 依据 core 参数、域名绑定及框架回退选择核心应用，不等同于直接假定是默认应用；例如 `?core=CMS` 可指定 CMS 上下文。没有目标脚本时 appFunc 走其回退跳转。普通应用按是否提供这些输出选择实现，不必创建空文件。

## 4. 根目录非 PHP 文件

| 文件 | 作用与边界 |
| --- | --- |
| `menu.json` | myStep 后台菜单数据，包含菜单组及条目。旧后台主模板请求该文件生成导航，插件管理接口可以增删扩展菜单，改后台入口时需同步链接。框架不把每个应用的同名 JSON 自动视为菜单。 |
| `menu.json.lock` | 菜单并发更新采用的旁路锁文件。属于运行辅助文件，不是另一份菜单配置；不作为新应用模板复制。 |
| `.DS_Store` | 系统目录元数据。与应用加载、设置、模块和模板均无关系，不纳入应用编写规范。 |

## 5. 文件之间应维持的对应关系

| 关联 | 应遵循的关系 |
| --- | --- |
| 应用身份 | 应用目录名 = info.app = 核心类名 = 核心文件主名；myStep 的核心类位置有明确例外 |
| 当前配置与安装配置 | config.php 保存当前值；应用需要安装初始值时由安装流程显式读取 config_default.php |
| 当前配置与编辑说明 | config.php 的键，与 config/ 的字段说明、控件和结构保持对应；配置值与说明文件不混用 |
| 后台入口与覆盖配置 | path_admin、route 声明、config_入口名.php、相关链接及设置保存关联处理同步调整 |
| 模块与模板 | 每个功能模块有明确对应模板，同一功能可以拆为 list／input 等用途；应用内部命名保持一致 |
| 模板与资源 | 模板 path/style/name 对应模板目录、风格和页面；风格资源使用对应 style，公用资源由 static 提供 |
| 路由与实现 | route 指向当前应用核心方法、lib 函数或明确登记的模块；不要依赖陌生请求值指定文件／方法 |
| 插件绑定与布局 | plugin.php 决定绑定关系，plugin_addon.php 在特定模块页面分支完成应用布局适配，二者分别维护 |
| 专项输出与脚本 | sitemap／rss／atom 框架入口对应所选核心应用根目录同名脚本，以及对应输出模板 |
| 磁盘路径与 URL | 配置持久化本地路径相对于 ROOT；URL 使用框架 URL 机制与 ROOT_WEB，不混用两种路径 |

`config/default.php` 是设置编辑说明的默认版本，`language/default.php` 是界面语言包默认版本，根 `config_default.php` 是显式使用的初始配置，三者名称相近但职责不同。

## 6. 哪些文件需要，哪些按功能增加

- 新普通应用以同名核心类、info、应用配置和页面入口为基本骨架，按页面功能设置 module 与 template 的对应关系。
- route、lib、global、plugin 以及各语言／编辑配置目录按实际功能提供；使用相应框架约定时保持约定名称和返回格式。
- config_default、config_入口名、setting_expand 取决于安装、分入口配置及保存关联需求，不能只复制文件而遗漏触发代码。
- plugin_addon、专项订阅／地图脚本，以及 sample、website 等扩展由具体应用功能决定。
- 应用应通过继承和框架接口使用公用能力，独立维护自己的功能；不得把应用专属基类、服务类或展示实现放入公用 lib。

## 7. 本次核查边界与源码依据

本篇列全两应用的实际顶层项目，未展开子目录内部文件规则。为确认触发时机，核对了框架和有关调用点，而非仅根据文件名称推断用途：

- `lib/myStep.class.php`：应用准备、默认入口、插件绑定、API、插件模块及应用专项输出。
- `lib/myRouter.class.php`：应用识别、匹配路由和入口配置覆盖。
- `lib/myConfig.class.php`：设置说明与结构加载。

## Admin 实例：同名核心与辅助实现均归应用

```text
app/Admin/
├── Admin.class.php          # 直接继承 myStep，认证、分发和应用公共接口
├── AdminService.class.php   # 按受信清单加载模块，提供模块共用能力
├── AdminStore.class.php     # 本应用配置版本及原子保存
├── pages.php                # 页面、模块、动作字段和菜单的固定映射
├── index.php / route.php    # 默认入口及显式路由，共用核心分发
├── lib.php                  # 明确引入应用辅助类
├── setting_expand.php       # 本应用设置保存的关联处理
├── info.php / config.php / plugin.php
├── config/ / language/
├── module/                  # 20 个独立功能模块，保留各功能业务
├── template/default/        # 主布局、功能模板与共享组件
├── asset/                   # 本应用的脚本和样式
└── README.md                # 应用维护说明
```

Admin 的 pages.php 和两个辅助类是本应用选择的组织方式，框架不会自动扫描所有应用的同名文件。其他应用可复用这种拆分思路，仍由自己的入口明确加载。应用核心及辅助类不再放入根 lib。
