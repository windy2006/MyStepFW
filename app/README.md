# MyStepFW 应用编写规范

整理日期：2026-10-18。本文为 app 目录中的应用开发与维护入口。

适用范围：基于现有框架开发和整理普通应用，运行目标为 PHP 8.5.12及以上受支持8.x版本。本文依据 myStep、CMS 的代码组织方式，以及已确认的应用目录、核心类继承和模块／模板对应规则编写。

普通应用提供自己的同名myStep子类，并通过module与template组织页面；通用能力由框架提供，应用专属逻辑保存在应用目录。

组件信息在本应用的`info.php`中声明，标识与目录保持一致；`name`用于展示，`ver`用于识别组件版本。变量、函数、方法及浏览器对象的写法见[命名规范](../docs/basics/09-naming.md)。

## 1. 目录归属

- 网站根目录的 `lib/` 负责公用框架能力，例如路由、配置、请求、数据库、缓存、模板和文件操作。
- 普通应用的核心类、辅助类、函数、模块、模板、配置及静态资源全部保存在 `app/应用名/` 内。
- 应用能够复用某段代码，并不自动意味着应把该代码放进 `lib/`；公共组件需要拥有独立于具体应用的职责和接口。
- myStep 是框架核心特例：执行引擎位于 `lib/myStep.class.php`，框架管理界面位于 `app/myStep/`。普通应用不照搬这种跨目录组织方式。
- 应用调用框架管理的 `cache/`、`files/` 等运行数据目录时，按框架配置使用；这些生成数据与应用源码的归属不同。
- 插件源码放在自身 `plugin/插件名/`，公用静态资源放在 `static/`，第三方组件按已有依赖机制管理。

规则按三个层次使用：同名核心类、继承关系和应用文件归属属于统一约束；模块、模板及有关入口按实际功能配置；应用的支持回退行为不代替新应用规范。纯数据 API 可以没有页面模板，具有展示功能的模块则应明确对应模板。

### 后台功能的强制组织规则

后台以 `plugin/manager/module/manager.php` 配合 `template/manager.tpl` 的模式为范例。每个功能的页面读取、动作处理和模板赋值放在自己的 `module/` 脚本，HTML 放在对应 `template/` 文件；不能再在应用根目录另设功能装配脚本、页面清单文件或独立辅助类文件。

```text
module/guide.php          → template/guide.tpl
module/function/api.php   → template/function_api.tpl
module/setting/main.php   → template/setting_main.tpl
```

模板允许按风格位于 `template/default/` 等目录，模块子目录用下划线连接为模板名；一个功能的列表、输入和局部模板仍归该功能维护。跨模块复用的应用函数、辅助声明集中在应用已有 `lib.php`，只做公共支持；页面执行与展示仍留在对应 module/template，不把页面业务堆入 lib.php。

根目录保留同名核心类及框架约定的入口、路由、元信息、配置、语言设置、菜单和扩展钩子。普通应用的核心类仍与应用同名并继承 myStep；插件使用其约定的 class.php，不混用两者的主类文件名。API 管理和框架指南也遵循以上布局，不作为例外。

## 2. 应用标识与核心类

以下名称必须一致，大小写也保持一致：

```text
应用目录：app/Hello/
应用标识：info.php 返回数组中的 app = Hello
核心文件：app/Hello/Hello.class.php
核心类名：Hello
继承关系：class Hello extends myStep
```

核心类由 `myStep::setPara()` 按当前应用目录和应用标识加载，作为本次请求的 `$mystep` 实例。当前加载方式查找全局类名，因此主类不改成需要另一套发现规则的命名空间类名。

```php
<?php
/**
 * 功能说明：Hello 应用核心，继承框架资源和生命周期功能。
 * 使用说明：由框架按应用名自动加载和实例化。
 */
class Hello extends myStep
{
}
```

即使暂时没有扩展方法，也保留同名核心类，明确应用边界。应用不重新实现框架已有的配置、连接、会话、模板、安全和输出机制。

## 3. 推荐目录结构

下面是普通应用的组织示例；语言、配置编辑、插件绑定等文件按功能需要增加。

```text
app/Hello/
├── Hello.class.php          # 同名核心类，继承 myStep
├── info.php                 # 应用标识、名称、版本和说明
├── config.php               # 当前应用配置
├── config_default.php       # 可选，安装初始配置
├── config_manage.php        # 可选，manage 路由入口的配置覆盖
├── index.php                # 默认页面分发入口
├── route.php                # 自定义路由／API 声明，按需提供
├── lib.php                  # 应用内复用函数与辅助声明，按需提供
├── global.php               # 页面公共数据准备，按需提供
├── plugin.php               # 本应用使用的插件标识，按需提供
├── plugin_addon.php         # 可选，插件模块页面的应用布局适配
├── plugin_layout.php        # 可选，通用插件后台布局回调
├── setting_expand.php       # 可选，配置保存的关联处理
├── sitemap.php              # 可选，站点地图专项输出
├── rss.php                  # 可选，RSS 专项输出
├── atom.php                 # 可选，Atom 专项输出
├── config/                  # 设置编辑说明与字段结构，按需提供
│   ├── default.php
│   ├── chs.php
│   ├── en.php
│   └── construction.php
├── language/                # 界面语言包，按需提供
│   ├── default.php
│   ├── chs.php
│   └── en.php
├── module/                  # 按功能拆分的处理脚本
│   ├── index.php
│   └── article/
│       └── content.php
├── template/                # 主布局和对应功能模板
│   └── default/
│       ├── main.tpl
│       ├── index.tpl
│       ├── article_content_list.tpl
│       └── article_content_input.tpl
├── asset/                   # 应用自己的样式、脚本和图片
│   ├── style.css
│   ├── function.js
│   └── default/
│       └── style.css
└── HelloService.class.php   # 可选应用辅助类，明确引入
```

当前实际模块目录名是 `module/`。模板可以直接放在 `template/`，也可以采用 `template/风格/`，由应用配置选择。安装器、站点配置等应用扩展也保留在自身目录中，不要求所有应用复制 CMS 的专属目录。

| 顶层目录 | 编写及配置规则 |
| --- | --- |
| `module/` | 按功能保存处理脚本；页面模块与模板对应；分组和动作由受控分发逻辑选择 |
| `template/` | 保存主布局和功能模板；名称、路径、风格由模板设置及模块选择决定 |
| `asset/` | 保存应用专属资源；基础资源和风格资源配套维护 |
| `config/` | 保存配置编辑说明及结构，与 config.php 中的实际设置字段保持对应 |
| `language/` | 保存界面语言包；与 config/ 中的字段说明语言文件分别维护 |
| `install/` | 需要安装时提供，由应用安装检查明确调用，执行配置及表结构初始化 |
| `website/` | CMS 多站点扩展；其他应用有同类需要时自行定义加载逻辑 |
| `sample/` | myStep 功能示例扩展；其他应用按需求组织自己的示例资源 |

页面应用的基本骨架包括同名核心类、info.php、应用配置、默认入口及模块／模板；按自定义路由直接输出的页面或纯 API 应用，可使用相应路由入口，但需要明确不支持的默认访问如何响应。功能扩展文件按需求提供，避免复制没有调用场景的空脚本。

## 4. 文件职责与命名

| 文件／目录 | 负责内容 | 编写规则 |
| --- | --- | --- |
| `info.php` | 应用元信息 | 返回包含 `app`、`name`、`ver`、`intro` 等字段的数组；app 与目录同名 |
| `应用名.class.php` | 应用公共能力及生命周期扩展 | 继承 myStep；各页面的业务处理继续按模块拆分 |
| `config.php` | 当前应用配置 | 返回配置数组，运行时覆盖全局对应项目；持久化本地路径相对于网站根 |
| `config_default.php` | 安装初始配置 | 由安装逻辑明确加载，用于生成当前配置；不是运行时自动补齐配置的约定 |
| `config_入口名.php` | 指定入口配置覆盖 | 与匹配路由入口首段关联；例如 CMS 的 config_admin_cms.php 选择后台风格 |
| `index.php` | 默认请求的页面调度 | 使用固定模块清单或受控映射；分发及公共装配保持简明 |
| `route.php` | 路由、格式及 API 声明 | 按需要定义 `$rule`、`$format`、`$api`；避免数据库写入和页面输出 |
| `lib.php` | 应用内部复用函数和辅助声明 | 命名空间与类声明显式组织；复用辅助类在本文件声明，不另建应用根目录文件 |
| `global.php` | 页面共享变量和模板数据 | 只承担当前应用页面公共准备；不要假定每种 API 分支都会加载它 |
| `module/` | 具体功能的数据处理和动作 | 按功能分组；页面功能具有明确对应模板 |
| `template/` | 页面结构和展示 | 使用 myTemplate 的变量、条件、循环和子模板组合 |
| `asset/` | 当前应用的前端资源 | 基础资源和风格资源可以分层，名称与框架收集规则对应 |
| `plugin.php` | 应用插件绑定 | 返回插件标识数组；执行仍取决于框架插件启用状态 |
| `plugin_addon.php` | 插件模块页面的应用布局适配 | 在框架文件模块展示且有主模板的有关分支调用，补齐应用导航、标签等展示数据 |
| `plugin_layout.php` | 通用插件后台布局适配器 | 返回接收插件HTML与上下文并返回myTemplate的回调，所有showPluginPage管理页共用；详见[插件规范第18节](../plugin/README.md) |
| `setting_expand.php` | 设置保存的关联处理 | 保存入口明确调用并提供上下文，同步入口配置、菜单及路由等关联内容 |
| `sitemap.php` | 站点地图输出 | 由框架 sitemap 入口选取核心应用后调用，使用对应输出模板 |
| `rss.php` | RSS 订阅输出 | 由框架 RSS 入口选取核心应用后调用，使用对应输出模板 |
| `atom.php` | Atom 订阅输出 | 由框架 Atom 入口选取核心应用后调用，使用对应输出模板 |
| `menu.json` | 菜单数据扩展 | myStep 后台显式读取；不是框架自动识别所有应用同名文件的通用约定 |

辅助类采用能明确归属的名称，例如 `HelloService`，放在本应用目录中。核心类加载应用自己的辅助类时可使用 `require_once __DIR__.'/HelloService.class.php';`。当前公用类加载器不会自动递归扫描所有应用，也没有自动把命名空间转换为目录的完整 PSR-4 规则。

这些脚本不能仅按文件名推断为全部自动执行：设置扩展、安装过程、插件页面适配和专项输出各有触发入口，具体调用条件见 [根目录脚本逐项说明](../docs/development/app/README.md)。`.DS_Store` 及菜单 `.lock` 文件属于系统元数据或运行辅助文件，不列入应用源码骨架。

## 5. 模块与模板必须具有明确对应关系

按“功能模块＋对应模板”拆分功能，使维护某一功能时能够直接找到处理代码和展示文件。同一模块可对应列表、输入、详情等多个用途模板，添加和编辑可共用输入模板。

| 实际应用例子 | 功能模块 | 对应模板 |
| --- | --- | --- |
| myStep 类加载设置 | `module/setting/class.php` | `template/setting_class.tpl` |
| myStep 域名设置 | `module/setting/domain.php` | `template/setting_domain.tpl` |
| CMS 后台文章内容 | `module/admin/article/content.php` | `template/admin/art_content_list.tpl`、`art_content_input.tpl` |
| CMS 前台首页 | `module/index.php` | `template/当前风格/index.tpl` |

新功能建议采用统一的“分组_对象_用途”命名，例如 `article_content_list.tpl`。现有应用已有的 `art_`、`func_`、`set_` 等前缀继续保持内部一致，不因统一规范机械改名。

对应关系由模块／分发代码明确选择模板。框架支持相应的加载能力，但不会自动推导所有嵌套模块与模板名。请求中的每个路径段也不必对应一个 PHP 文件，例如 `add`、`edit`、`list` 可以是内容模块内部的动作。

核心类、服务类和页面清单可以复用公共处理，但不应把所有功能实现集中进一个巨大的类或入口脚本，削弱模块与模板独立维护的结构。

## 6. 统一入口与生命周期

所有请求由网站根入口承接，应用不另行调用 `myStep::init()`、启动另一套 Session 或重复加载 Composer。

主要关系如下：

```text
网站 index.php → myStep::init / go
    → 识别应用及路由，合并相应配置
    → 加载 应用名.class.php，创建 $mystep
    → 加载应用 lib.php，执行可选 preload()
    → 准备框架资源、服务、会话及认证上下文
    → 命中路由：执行声明的处理链
      默认入口：global.php → index.php → 对应模块
    → 模块准备数据 → 渲染对应子模板 → 主模板输出 → 请求收尾
```

这是普通请求的主干，静态文件、API、插件模块和直接响应有各自分支，具体见 [通用详细执行流程](../docs/backend/runtime/execution.md)。

- `preload()` 在框架默认会话启动和登录恢复前执行，适合准备应用服务，不能据此假定用户已登录。
- 页面共享数据放在合适的页面公共准备阶段；身份和权限检查放在认证上下文已建立的执行阶段。
- 应用扩展 `start()`、`end()` 等生命周期时，需要核对父类职责、签名和相应父类调用，避免跳过框架处理或重复执行。
- 默认入口可以把主模板 `$tpl` 和内容 `$content` 交回外层输出；直接路由处理器根据该分支自行完成响应。确认输出由谁负责，避免重复 `show()`／`end()`。

## 7. 路由与链接

- 普通应用默认路径前缀使用应用名；后台别名、域名绑定及自定义路由通过框架配置和应用路由声明实现。
- 路由模式支持 rewrite、path_info、query_string；页面链接通过框架 URL 功能或应用封装生成，查询参数统一编码。
- 维护自己的 `route.php`；根 `config/route.php` 是汇总生成的路由注册表，不作为应用路由源码编辑。
- 路由文件会参与编译和更新检测，不把它当成每次请求必执行的应用初始化文件。
- 文件包含目标、类名、方法名、模板名等由受控映射决定。不要直接把请求值拼成可执行文件路径。
- 为未知模块和不支持的方法明确返回对应状态；页面、API、写操作各自保持清晰入口及授权边界。

## 8. 配置、路径和语言

配置文件通常返回 PHP 数组。应用 `config.php` 覆盖全局对应项目；命中路由时还可能合并 `config_入口名.php`，CMS 的 `config_admin_cms.php` 即用于切换后台模板风格。

必须区分以下三种 default：

| 文件 | 用途 |
| --- | --- |
| `config_default.php` | CMS 等应用的安装初始值，由安装代码显式加载；不是通用运行时自动加载约定 |
| `config/default.php` | 默认语言的设置字段说明／控件定义，可转引 `chs.php` |
| `language/default.php` | 默认界面语言包，可以转引实际语言文件 |

`config/construction.php` 保存字段类型等结构，与 `config/chs.php` 等详细说明配合 myConfig 使用。新增设置字段需要同步配置值、编辑说明、结构及调用代码。

后台路径设置须按应用现有约定使用：myStep 使用 `gen.path_admin`，CMS 使用 `web.path_admin`。入口名称改变时，同步路由、`config_入口名.php` 及有关链接；模板风格由配置内容选择，不要求与入口名相同。新增保存入口时，需要明确实现 setting_expand 的等效关联处理，不能假定放置文件就会自动生效。

持久化的本地配置路径相对于网站根目录，例如：

```php
return ['template' => [
    'name' => 'main',
    'path' => 'app/Hello/template',
    'style' => 'default',
]];
```

运行时按 `ROOT` 或 `myPath::absolute()` 解析；当前应用运行目录使用框架提供的 `PATH`，应用内部固定文件也可使用 `__DIR__`。URL 使用 `ROOT_WEB` 和框架 URL 接口，不把磁盘路径用于页面链接。

类加载“特别指定”的值相对于该条规则目录，是配置相对基准的明确例外；详见 [路径规范](../docs/backend/runtime/constants.md)。

框架先加载 myStep 的界面语言，再叠加当前应用的同语言文件。应用应提供所支持的语言文件；不要假定缺失的任意语言文件总会自动回退到 `default.php`。

## 9. 模板、资源和框架服务

- 模板调用继续使用 `myTemplate`，遵循应用配置的 `path`、`style`、`name`，通过 `assign()`、`setLoop()`、`setIf()` 准备展示数据。
- 页面结构保存在 `.tpl`；主模板负责布局，子模板负责功能内容，表单处理和数据库操作留在 PHP 中。
- 主模板按现有模式保留 `main`、`page_start`、`page_end` 等输出位置，以承接内容、资源及框架安全处理。
- 外部文本根据 HTML、属性、URL 等输出位置转义，避免重复转义；只有受信的已渲染子模板内容作为 HTML 插入。
- `asset/style.css`、`asset/function.js` 及当前风格下的对应文件由框架收集；其他应用资源使用框架应用资源入口访问。
- 使用 `$mystep`、`$ms_setting`、`$db`、`$cache`、`$info_app`、`$tpl_setting` 等框架上下文，不创建重复的全局服务体系。
- 在普通函数内明确传参或声明所需 `global`；应用命名空间中使用框架类时采用 `\myTemplate`、`\myReq` 等完整类名。
- 数据库按应用实际需求连接，查询值使用绑定参数或合适的构造接口，标识符使用固定值／白名单；安装建表由独立步骤完成。
- 用户相关页面和权限响应明确设置缓存策略；缓存按应用及业务维度区分，失效清理与写入调用同步维护。

## 10. 安全、注释与验证

- 所有受保护页面和接口都检查身份及业务权限；写操作采用适合的请求方法并经过框架 CSRF 保护。
- 输入检查包含类型、长度、范围和数组形状；服务方法被另一入口调用时，也要确认该入口的鉴权及校验。
- 输出和日志不包含数据库口令、会话标识等敏感配置。
- PHP 源码、依赖和语法遵循当前 PHP 8.5.12 最低版本与 Composer 约束。文件提供功能说明、使用说明和方法目录；方法提供功能、参数、返回值及必要异常说明。
- 调整公共方法、配置字段或模板变量时，同步核查应用、插件、脚本和文档调用。
- 验证重点包括实际模块与模板的对应、默认／自定义路由、三种 URL 模式、子目录部署、登录权限、保存后的跳转以及所用模板风格。

## 11. 开发顺序与关联维护

### 从新建应用到功能完成

1. 确定唯一应用标识，建立目录、info.php 和同名核心类，声明继承 myStep。
2. 编写应用配置，明确模板、语言、数据库、会话及缓存需求；设置值及应用专属实现留在应用目录。
3. 明确默认入口、自定义页面路由、API 和后台入口的分工，再确定模块清单与分发映射。
4. 按功能建立模块及对应模板，选择统一前缀和用途后缀，使用框架资源和数据调用接口。
5. 准备公共页面数据、应用复用函数、语言及前端资源，保持类、函数和展示的职责边界。
6. 根据实际需要接入配置编辑与保存关联、安装、插件、地图和订阅输出，明确每个扩展的调用方及上下文。
7. 验证功能入口、对应模板、实际应用核心实例、权限、保存结果和框架支持；同步使用说明。

### 修改一项功能时要同步哪些部分

| 变更 | 必须核查的关联 |
| --- | --- |
| 新增或调整页面功能 | 模块、对应模板、分发映射及有关路由、菜单、权限、语言、资源 |
| 新增配置字段 | 当前配置、安装默认值（若有）、编辑说明、字段结构、读取代码和保存关联处理 |
| 修改后台入口 | path_admin、route、config_入口名.php、菜单／表单／跳转链接和保存扩展逻辑 |
| 增加模板风格 | 模板 path/style/name、配套资源、模块选择及必要的展示适配 |
| 接入插件模块 | 插件安装／启用状态、应用绑定、模块登记、权限以及是否需要 plugin_addon 布局适配 |
| 增加地图或订阅 | 核心应用选择、同名专项脚本、对应模板、站点配置、输出格式和缓存 |
| 调整辅助类或公共方法 | 文件加载顺序、继承／调用关系、路由回调、框架及插件调用点、文档与相关验证 |
| 修改业务数据 | 受保护写入入口、数据校验、数据库操作、受影响的列表／详情及缓存失效 |

模块与模板的对应不只体现在命名，也体现在维护范围：修改某个功能，应能找到它的处理代码、展示结构、配置和资源；公共机制承担重复处理，功能边界仍然清楚。

## 13. 文件调用条件速查

| 阶段／入口 | 调用或使用的文件 | 关键条件 |
| --- | --- | --- |
| 路由发现及重建 | info.php、route.php、应用配置 | route 是声明源，不能承载每次请求必须执行的初始化 |
| 建立当前应用上下文 | 应用名.class.php、lib.php、可选 preload | 核心类按应用名查找；preload 不能假定框架会话已启动 |
| 默认页面请求 | global.php → index.php → module → template | 具体模块选择由应用实现；显式路由可能不经过 index |
| 页面功能模块请求 | 当前应用配置及框架 getModule 分发 | 按风格／模块回退规则选择文件，不应把任意请求路径直接 include |
| 配置编辑与保存 | config.php、config/、setting_expand | 编辑说明与配置值分开；保存调用方明确接入关联更新 |
| 安装初始化 | install/、config_default.php | 由应用安装检查或明确入口调用，不是放置目录就自动执行 |
| 应用绑定插件 | plugin.php | 只声明标识列表，仍受全局活动状态及插件初始化条件约束 |
| 插件文件模块嵌入应用 | plugin_addon.php | 仅有关布局分支显式调用，不是所有插件或页面的通用钩子 |
| 地图、订阅输出 | sitemap.php／rss.php／atom.php | 框架专项入口选择核心应用后调用同名脚本 |
| 前端资源 | asset/style.css、asset/function.js、风格下同名文件 | 框架收集对应资源；其他图片和文件走允许的资源入口 |

根脚本职责按本文约定处理，开发步骤见[应用实战](../docs/development/app/README.md)。插件的独立结构及与应用的关系见 [插件文件结构、命名与脚本职责](../docs/development/plugins/README.md)。
